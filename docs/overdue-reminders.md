# Overdue receivables reminders (P2.6)

Finance staff assigned to the selected facility and OperatorAdmin can create in-app reminders under Reports. Select a customer organization, facility, due-date interval and source page, then choose **Create overdue reminders**. The interval is half-open, at most 366 days; page numbers are zero-based, 0..99. At most 5000 matched statements are accepted; each page contains 50 source statements including settled and current rows. Follow the returned next source page rather than assuming every source row creates a notice. Each command observes current records, so pages are not a frozen multi-page snapshot.

Only positive reconciled outstanding balances with a due date strictly before the facility-local aging date generate reminders. Due today remains current. Reconciliation uses the same linked credits, allocations, deposit deductions and allocation releases as [receivables](receivables.md). Held deposits, unapplied or unverified receipts and pending online payments do not pay statements. A negative reconciliation returns409 without any reminder or successful command receipt. Amounts are rendered as exact integer strings, including values beyond JavaScript's safe integer range.

A unique statement/local-date business key permits one reminder per statement per facility-local day. Fresh overlapping or concurrent commands count existing reminders as duplicates. Each notice identifies the statement, due date, outstanding VND, observation UTC and local date. These are historical events: after a payment the old notice remains unchanged and a new command rereads the settled balance. Customers must inspect the current statement before paying. No interest, penalty, payment, allocation or new statement is created.

The command immediately writes the outbox and in-app notice together with its audit and idempotency receipt. FacilityManager dispatch is not needed for these notices. Customers read them in the existing organization/facility In-app notices feed. This is explicit in-app delivery, not email transport or a background scheduler. Existing lease-ending/stock manager jobs remain available separately.

API: `POST /api/v1/organizations/{organizationId}/facilities/{facilityId}/receivable-reminders` with JSON `{ "startDate": "2026-10-01", "endDate": "2026-11-01", "page": 0 }`. Include current session/CSRF and a UUID `Idempotency-Key`. The body and selected organization/facility are bound to the receipt. Replay returns the same result; changed payload/scope conflicts409. Current identity, active customer and current Finance grant are checked again inside the transaction before a previous success can be returned. Other roles and inaccessible resources return404.

The result includes observedAt, asOfDate, timeZone, scanned, eligible, created, duplicates, page and nextPage. No client-side money arithmetic is used. If a response is lost, keep Reports open and retry the original reminder command with its original key/body after restoring the same account/scope and Finance permission. The UI freezes inputs while outcome is uncertain. Switching scope hides previous-scope results; reloading or leaving Reports loses this in-memory recovery state. Server daily deduplication remains effective, but a fresh command is not an exact readback of the lost receipt.

No new schema, external provider or dependency is required. SQL/TestServer and React checks do not establish deployed/browser/accessibility or real merchant acceptance. See the coordinator checkpoint/review evidence for the exact source and local runtime handoff status.

Reminder command receipts carry `readbackPolicy: CurrentFinance`. Both POST replay and GET command recovery require current active identity/customer/facility and Finance access (or OperatorAdmin); a retained customer membership does not grant receipt access. Other command receipts, including customer hosted payments, retain their existing access rules.
