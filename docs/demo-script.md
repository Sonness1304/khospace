# Synthetic local demo walkthrough

This walkthrough uses only the seeded `.test` accounts and a new `WarehouseRent_Demo_*` database. It is a portfolio scenario, not a payment processor or production accounting system. Follow the local setup in [README](../README.md); keep IDs and versions from the displayed readbacks. The app does not persist an unresolved browser command after a reload.

1. Sign in as `admin.a@example.test` with the public demo-only password in the README. Select Customer A and a published facility. In **Space & quotes**, search for a unit for a period beginning today and ending two days later. Request a quote and create a hold. Record the booking ID, rental account ID and required deposit. A quote alone does not reserve a unit; a hold expires after 15 minutes.
2. Sign in as `finance@example.test`, select the assigned facility and open **Finance**. Read the rental account. Record a synthetic receipt equal to the required deposit with a unique reference and evidence reference, verify it, then allocate the verified amount to Deposit. If the rounded deposit is zero, explicitly verify zero instead of inventing a receipt.
3. Sign in as `sales@example.test` and select the same facility. Read the booking by ID in **Rental desk**, confirm it and create the lease. Save the lease ID. Sign in as `manager@example.test`, read the lease and complete handover after checking the inspection box. Read the lease again to obtain its stable lease-unit ID.
4. Sign back in as Customer A. In **Stock requests**, create a synthetic item, then a receipt instruction for 10 boxes using the lease and lease-unit IDs. Submit it. As `clerk@example.test`, read the request, approve it, enter the actual quantity 10 and post it. Repeat for an issue instruction of 7 boxes. As Customer A, read **Inventory** for the same lease-unit: the balance is 3 and the history contains both postings.
5. As finance, read the rental account, issue the agreed calendar-month statement after handover, record and verify a separate synthetic receipt and allocate part of it to the statement. The deposit remains a separate liability; the statement shows the outstanding amount. These entries do not contact a bank or generate a tax invoice.
6. Explain the safeguards: all unit holds use database locks, handover records actual custody separately from the schedule, stock postings are append-only, and verified funds cannot be allocated twice. The manager cannot clear space while stock or pending requests remain.

If a command response is uncertain, keep the current page open and use its **Read ... command** action before retrying. A page reload loses the in-memory pending identity; do not assume the action failed. Browser acceptance, accessibility and a recorded demo remain unverified until tested against a permitted running host.


## P1 extension after the baseline

Before a later permitted runtime demonstration, inspect the fresh [P1 candidate](deployment.md) and compare `/health/build` with its source SHA/latest migration. Every action below uses only synthetic data. Keep readback IDs and displayed versions. These are manual acceptance steps, not a claim that browser QA already ran.

1. **Renewal and commercial versions:** CustomerAdmin accepts a same-unit renewal quote; Sales confirms/applies it with current lease/quote versions. Read the new commercial version and retained lease-unit grant IDs. The existing deposit stays unchanged. Finance issues added rent or the unique supplement if the month was already issued. See [renewal](renewal-workflow.md).
2. **Inventory corrections:** Rent/handover a second unit in the same customer/facility before demonstrating transfer. Transfer stock atomically, read paired ledger entries, reverse a permitted full original posting once and verify nonnegative balances. Create a count with one manager; a different manager approves it against the observed balance version. Use partial fulfillment only within the approved cumulative quantity. See [inventory corrections](stock-corrections.md).
3. **Settlement:** Finance reads an issued statement, records an approved credit/service correction and verifies the original issued statement remains unchanged. Paid credits release allocations; deposit liability and unapplied funds remain separate. Record only synthetic manual refund/deduction evidence. Clear physical custody only after zero stock and no pending instructions/counts. Close the account only when every displayed blocker is resolved; reread Closed and verify historical scheduled metrics remain. See [settlement](settlement-workflow.md).
4. **Private lease evidence:** Customer member uploads a small safe synthetic PNG/JPEG/PDF with lease ID and reason. Read/download as the same customer; Customer B must not see it. CustomerAdmin/manager revokes it; its old download link must fail after revocation. Do not upload real personal documents. See [private documents](private-documents.md).
5. **Access administration:** OperatorAdmin grants/revokes a seeded non-admin staff identity's facility role with reason/current directory version. Verify revoked access and disabled sessions. CustomerAdmin may queue a synthetic invitation; recovery uses generic feedback. External email delivery is unavailable, so do not describe a queued token as delivered or extract actual account secrets. See [identity operations](identity-operations.md).
6. **Notices and reports:** Manager queues an eligible page then dispatches the pending batch. Repeat the job and verify no duplicate event. Customer reads only its selected organization/facility notices. Report chosen interval scheduled area-days separately from current custody and gross receipts/deposit liability. Export scoped stock/statement CSV; verify authorized rows and formula-safe text. See [reports and notices](reporting-notices.md).
7. **Recovery explanation:** Run the separately documented synthetic SQL restore rehearsal only on its own GUID fixtures. Explain preserved allocation, custody, ledger, effective funds and private access/hash evidence. Do not restore onto the demonstration database. Cross-host keys, timing SLA and production recovery are not proved.

Capture browser/manual outcomes only when the inspected application is permitted to run. Component tests and the compiled candidate do not establish visual/accessibility acceptance. The source remains English; the owner/coordinator communicates in Vietnamese.
